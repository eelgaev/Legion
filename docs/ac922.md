# Legion on the IBM AC922

The IBM Power System AC922 is one of Legion's two first-class machines, together with the DGX Spark. This page
covers what the machine needs: the operating system, kernel and driver, the compiler, the build, and how
to run on it. The performance tables are in the [README](../README.md#performance), and the command lines
behind them are in [run/ac922/](run/README.md#ibm-ac922).

## The machine

- Two POWER9 sockets (ppc64le) and four Tesla V100-SXM2 16 GB GPUs (Volta, `sm_70`).
- **NVLink 2.0 between the CPUs and the GPUs**, not only between GPUs. Each socket has an NVLink pair of
  GPUs: GPUs 0-1 sit on NUMA node 0 and GPUs 2-3 on node 8, and the two GPUs of a pair are also linked to each other.
- With the right kernel and driver (below), the GPUs read host memory **in place** over NVLink through ATS
  (address translation services: the GPU walks the CPU's page tables), and each GPU's HBM is onlined as a
  coherent, memory-only NUMA node. This is unified memory in hardware, the property Legion is built around.

Measured bandwidth (see [bandwidth.md](bandwidth.md)):

| Path | Bandwidth |
|---|---|
| V100 HBM2, device memory | 894 GB/s |
| One GPU reading pinned host memory on its own NUMA node | 68.5 GB/s |
| Both GPUs of one socket together | 133-135 GB/s |
| A GPU reading the other socket's memory | 46-56 GB/s |

Legion uses the host link for:

- **Host-resident MoE experts** (`--experts cache`): the routed experts live in host memory. The most used
  ones are cached in VRAM, and the rest are read in place over NVLink during the step.
- **The host KV tier** (`--kv-host-tokens`): KV cache past what fits in VRAM.

Models far larger than 4x 16 GB, such as Qwen3.8-Flash-Next and GLM-5.3-Flash, therefore run at full speed
only when CPU-GPU NVLink, ATS and coherent GPU memory all work.

## Operating system, kernel and driver

### Requirements

| Component | Requirement |
|---|---|
| Userspace | **RHEL 8**. NVIDIA's ppc64le userspace (driver libraries, CUDA) is RHEL 8 only. |
| NVIDIA driver | **550.54.15**, the last NVIDIA driver release for ppc64le. |
| CUDA toolkit | **12.4**, the last CUDA release for ppc64le, matching that driver. |
| Kernel | One with POWER9 NVLink2 / NPU support: RHEL 8's own 4.18 kernel, or (recommended) a current kernel with the patches below. |
| Compiler | **gcc-toolset-12** (see [Building](#building)). |

### Why the kernel matters

POWER9's CPU-GPU NVLink goes through the NPU (NVLink processing unit), and the kernel has to set it up.
Mainline Linux removed the POWER9 NVLink2 / NPU support in two steps, in 5.3 and 5.13. On a stock
current kernel with the 550.54.15 driver, the GPUs work, but **without CPU-GPU NVLink, ATS, coherent GPU
memory or unified memory**. That is the path Legion's host-resident experts depend on.

RHEL 8's 4.18 kernel still has the support and works.

### Recommended: a current kernel with the power9-nvidia-nvlink2 patches

[power9-nvidia-nvlink2](https://github.com/eelgaev/power9-nvidia-nvlink2) brings the support back on current
kernels. It targets POWER9 bare metal (OPAL/skiboot) with NPU2 and V100-SXM2. It has two parts:

- **Kernel patches**, for mainline **6.12 LTS** (`kernel-patches/mainline-6.12`, built from a kernel.org
  tarball with `build-mainline.sh` and the shipped config) or for RHEL 9.9's 5.14 kernel
  (`kernel-patches/rhel-9.9`). They restore:
  - NPU PHB probing at boot;
  - the OPAL calls;
  - a missing secondary-TLB invalidation;
  - the `nvlink2-npu` module, which provides the NPU2 API the NVIDIA driver expects.
- **NVIDIA driver patches** for 550.54.15 (`nvidia-patches/550.54.15/apply.sh`, then a DKMS build against
  the new kernel). There are six:
  - a removed kernel API;
  - an ATS enablement gate;
  - three ATS servicing fixes;
  - a bounded wait for an unresponsive GPU (the new `nvidia-uvm` option `uvm_channel_init_timeout_sec`).

The kernel runs under the RHEL 8 userspace; follow the repository's README for the build and install
steps. The AC922 numbers in Legion's README were measured on the patched 6.12 kernel. Compared with RHEL 8's
4.18 kernel, its smaller memory blocks leave each V100 about 0.75 GiB more usable VRAM, all of which goes
to the KV cache and the expert cache.

### Checking the setup

- `nvidia-smi nvlink -s` lists the links of each GPU as active.
- `numactl -H` shows the two CPU nodes (0 and 8) plus one memory-only node per GPU (the onlined HBM).
- `legion serve --device cuda` prints a startup report on a terminal. It lists per GPU and per NUMA node
  where the weights, KV cache, expert slots and host arenas went.

## Building

The system compiler of RHEL 8 (gcc 8) is too old for Legion's CUDA build. Install **gcc-toolset-12** and enable
it in every shell that builds:

```sh
sudo dnf install gcc-toolset-12
source /opt/rh/gcc-toolset-12/enable
```

Then build with the AC922 profile, which sets `CMAKE_CUDA_ARCHITECTURES=70` and the compilers:

```sh
git submodule update --init third_party/ggml
scripts/build.sh ac922
# equivalent:
source /opt/rh/gcc-toolset-12/enable
CC=gcc CXX=g++ CUDAHOSTCXX=g++ CMAKE_CUDA_ARCHITECTURES=70 cargo build --release --features cuda
```

Notes:

- `CUDA_PATH` / `CUDA_HOME` must point at the CUDA 12.4 toolkit (the default is `/opt/cuda`). `build.rs`
  searches `targets/ppc64le-linux/lib` too.
- ggml's CPU backend on POWER uses the VSX `vector` keyword, which needs GNU C++ (`gnu++17`). Do not force
  `CMAKE_CXX_EXTENSIONS=OFF`.
- `GGML_NATIVE=ON` (the default) builds for the POWER9 of the build machine.

More detail is in [building.md](building.md#ibm-ac922-power9-ppc64le-v100).

## Running

- **NUMA placement is automatic.** `--numa auto`, the default, binds threads and pinned host memory to the
  NUMA node of the GPUs in use, so each GPU reads its own socket's memory (68.5 GB/s rather than 46-56).
- **Two GPUs: use one NVLink pair**, GPUs 0,1 or 2,3 (for example `CUDA_VISIBLE_DEVICES=2,3`). On a
  layer split over one pair, `--expert-peer-fetch` is on by default. While one GPU runs its layers, its idle
  peer copies half of the missed experts from host memory over its own link.
- **Four GPUs:** `--gpus 4` splits the layers over all four GPUs, one pipeline stage each.
- **Models bigger than VRAM:** `--experts cache` keeps the routed experts in host memory and caches the most
  used ones in VRAM.
- **Tensor parallel:** `--tp 2` runs over an NVLink pair. `--tp-replicas` runs one copy per pair.
- **BF16 checkpoints:** the V100 has FP16 tensor cores but no BF16 ones. `--weights-fp16 load` converts BF16
  weights to FP16 while loading. It is opt-in because outputs shift slightly.
